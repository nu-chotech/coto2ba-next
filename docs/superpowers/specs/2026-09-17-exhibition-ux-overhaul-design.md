# 技育博に向けた UI/UX 刷新とマルチプレイ — 設計

> 作成: 2026-09-17 / 対象: 技育博（〜2026-10 上旬）本番
> 前提の確定経緯は本ドキュメント §1。実装計画は `docs/superpowers/plans/` に分割する。

## 1. 確定した前提

実機プレイのフィードバックと対話で、以下が確定した。

| 項目 | 確定内容 |
| --- | --- |
| 本番 | 〜2026-10 上旬（3 週間以内） |
| 展示形態 | ブース端末 2〜3 台 ＋ 持ち帰り QR の両方 |
| 山場 | 「混ぜる」と「図鑑」の 2 段構え |
| トーン | **静かな土台＋演出で爆発**。レイアウト・ナビ・部品は iOS 純正に徹し、「混ぜた瞬間」と「クリア」だけ派手にする |
| 図鑑 | **「自分の軌跡」を主役**にする |
| マルチプレイ | **本格的に入れる** |
| 効果音 | **合成音を自作して同梱**（ライセンス問題ゼロ、音色を統一できる） |

実機で良い評価だったもの（**壊さないこと**）: 実装ロジック、Liquid Glass のタブバー操作、ハプティクス。

## 2. 目標と非目標

**目標**: 展示で「触った人が声を出す」水準まで UI/UX を引き上げ、ブースで複数人が同時に競える状態にする。

**非目標**: Tier B（Apple Developer Program）、`08_embeddings`（OOV 解釈）、LLM フレーバー、`feat/shareable-craft-prototype` の取り込み（展示後に回す）。

## 3. バグ修正（最優先・独立して進む）

### 3.1 `/api/me` が常に検証に落ちる

**症状**: 設定画面で表示名変更・ブースモード切替をすると「サーバーの応答を解釈できません」。

**原因**: Zod 4 の `z.record(enumSchema, valueSchema)` は**列挙キーの網羅を要求する**（Zod 3 からの破壊的変更）。`packages/contracts/src/schemas.ts:53` の
`best_free_moves: z.record(difficultySchema, z.number().int().positive())` に対し、
サーバーは通常 `{}` を返すため **`/api/me` のレスポンスが毎回落ちる**。
GET は握り潰す設計なので不可視、PATCH（mutation）だけがエラー文言として表面化していた。

**修正**: `z.partialRecord(difficultySchema, …)` に変更する。

**回帰テスト**: `packages/contracts/tests` に「`best_free_moves` が `{}` / 部分 / 全部 のいずれでも通る」を追加。
`z.record` の網羅要求に将来また嵌らないよう、**契約テストとして固定する**。

### 3.2 図鑑に自分の語が出ない

**症状**: クリアしても図鑑が「まだ語に出会っていません」のまま。

**原因**: 本番 Neon の `vocab.pos3` が **102,520 語すべて NULL**（ローカルでは計算済み）。
`pos3` が無い語はシーンから除外されるので `ownedCount` が 0 のままになる。バグではなくデータ欠損。

**修正手順（容量に注意）**: Neon は 318MB / 512MB。102,520 行の一括 `UPDATE` は
死んだタプルで容量を食い切る危険がある。**バッチ更新＋間に `VACUUM`** で流し、
各バッチ後に `pg_database_size` を確認しながら進める。完了後に `pos3 IS NULL` が 0 件であることを検証する。

### 3.3 ヒントが機能していない

**症状**: ヒントの語を使っても順位が上がらない。

**原因**: 現行は `v_hint = 0.8·v_current + 0.2·v_goal` の**近傍**を返す（`apps/api/src/services/vector.ts:158`）。
しかし実際の手は「現在 と 入力語 を混ぜる」なので、**すでに現在とゴールの中間にある語**を混ぜても
結果は現在からわずかしか動かない。ゴールに乗せるのに必要なのは内挿ではなく**外挿**である。

比率 `r` でゴールに着地させたい入力語のベクトルは

```
v_W*(r) = (v_goal − (1 − r)·v_current) / r
```

**修正設計**:

1. `RATIOS` の代表値ごとに `v_W*(r)` を作り、HNSW でそれぞれの近傍 k 件を集めて候補集合 C とする（安い）
2. C の各語 W について、全 `r` に対する `cos(blend(v_current, 1−r, v_W, r), v_goal)` を計算し、最良の `r` を選ぶ（純粋な算術）
3. 上位の少数だけ**実際の混合**（HNSW で最近傍を引く）を走らせ、**結果語のゴール類似度が現在より高いものだけ残す**
4. 既存の表記揺れ除外（`isMorphologicalVariant`）と登場済み語の除外はそのまま適用

**契約変更**: ヒントは `string[]` から `{ word, ratio }[]` に変わる。
**推奨比率まで提示する**ほうが「混ぜ方」自体を教えられて親切で、混合の仕組みの理解も進む。
ヒント使用はランキングのタイブレークに残るので、難易度は壊れない。

**検証（必須）**: 「ヒントに従うと rank が改善する」を**統計で担保**する。
ゴールプールから 100 局面を抽出し、各局面でヒント 1 位を提案どおりの `r` で適用して
rank の改善率を測る。**改善率が現行を明確に上回ることをテストで固定する。**

## 4. デザインシステムの刷新

### 4.1 Liquid Glass の統一

`PrimaryButton` は「`GlassView` の `opacity: 0` が描画されない」問題を避けるため
**意図的にガラスを使っていない**。これが「中途半端に普通のボタン」の正体。

**対応**: `GlassButton` を新設し、フェードは `GlassView` 自体ではなく
**親レイヤーの opacity** で行うことで既知の問題を回避する。
`canUseLiquidGlass()` が false の端末では現行の `BlurView` フォールバックに落ちる。
主要な操作面（混合ボタン、シート、ロビーのカード、結果画面のアクション）をガラスに揃える。

### 4.2 絵文字の追放

実績アイコンは**最初から SF Symbols 名**（`sparkle` / `crown` / `flame.fill` …）で定義されており、
`expo-symbols` も依存に入っている。**絵文字にフォールバックしていただけ**なので、
`SymbolView` で描画するアイコンコンポーネントを 1 つ作って全面的に差し替える。
Android / Web には同義の代替を用意する。

**例外**: シェアテキストの `⬜🟩🟦🟨`（Wordle 形式）は**残す**。
これは X に貼られる文字列で、SF Symbols では代替できず、絵文字であること自体が機能している。

### 4.3 タイポグラフィと余白

「しょぼい」の実体の多くは**余白とヒエラルキーの不足**である。
Apple の標準的なメトリクス（Large Title、セクション余白、44pt タップ領域、
セーフエリアの扱い）に合わせて `theme/tokens.ts` を見直す。

## 5. 画面フローの立て直し

**現状の問題**: ギブアップが `Alert.alert('メニュー', …)` の入れ子（`play/game/[id].tsx:184`）に埋まっており、
「閉じる / ギブアップ」の二択が Alert で出る。iOS の作法から外れていて発見しづらい。

**対応**:

- ゲーム画面にネイティブのナビゲーションバーを持たせ、**右上に `ellipsis.circle` のメニュー**を置く
- メニューは Alert ではなくネイティブのコンテキストメニュー
- ギブアップは破壊的操作として確認を 1 段だけにする（現状の 2 段 Alert は過剰）
- ロビー → ゲーム → 結果 → 図鑑 の遷移を、戻る操作が自然になるよう整理する

各画面について「Apple 純正アプリならどう置くか」を基準に、タイトル・戻る・主要操作の位置を決める。

## 6. ratio のホイール化

**背景**: オリジナルは iPod のクリックホイール風に比率を回して決める UI で、そこが作品のこだわりだった。
現行は水平スライダーに退化している（`components/MixSlider.tsx`）。

**設計**: `react-native-gesture-handler` の `Gesture.Pan()` で**指の角度**を取り、
8 段階の `RATIOS` にスナップする回転ホイールにする。Skia で目盛りと針を描画。

- 段が変わるたびに `selectionAsync` ＋ クリック音（既存の `slider_detent` の流れを踏襲）
- **値は連続値にしない**（`RATIOS` の 8 段階のみ）。サーバーが厳密一致で検証しているため
- 慣性を許し、離したときに最寄りの段へバネで収まる
- 新しいネイティブモジュールは不要（Expo Go の絶対制約を満たす）

既存の `MixSlider` は削除し、`MixWheel` に置き換える。

## 7. 図鑑の再設計 — 「自分の軌跡」

**現状の問題**: 全語が等しい点として浮かぶだけで、何を見ればいいか分からない。操作も重い。

**設計**:

- **主役は経路**。`start → 各手 → goal` を光る折れ線で描き、節に語のラベルを付ける
- ゴースト点は**背景に降格**（小さく・暗く）。主役を邪魔しない
- 開いた瞬間に**選択中の経路が画面に収まるようカメラを自動フレーミング**する
  （いまは「とりあえず点群の前に放り出される」ので意図が伝わらない）
- 上部は検索ではなく**経路の切り替え**（今日 / 過去のクリア）を既定にする
- 結果画面から「この軌跡を見る」で直接その経路にフォーカスして入る
- タップで語のシートを出すのは現行どおり

**操作性**: 回転の自由度が高すぎて迷子になるのが重さの原因なので、
ピッチに制限を設け、二本指で経路中心に戻れるようにする。リセットは常時見える位置に置く。

## 8. 効果音（合成）

**制約の確認**: Expo Go ではネイティブのシステムサウンド API
（`AudioServicesPlaySystemSound` 相当）は**叩けない**。ネイティブモジュールの追加は
CLAUDE.md の絶対制約に抵触する。使えるのは `expo-audio` で同梱ファイルを鳴らす経路のみ。

**設計**: `tools/pipeline/scripts/11_sounds.py` を追加し、Python 標準の `wave` ＋ numpy で
サイン波ベースの短い音を生成して `apps/mobile/assets/sounds/` に出力する。

- 音色を 1 つの倍音構成から作るので**全イベントで統一**が取れる
- 減衰は短く、耳に痛くない帯域に収める（iOS 純正の UI 音に寄せる）
- `src/lib/feedback.ts` の既存のイベント対応表に流し込むだけで鳴る
- 自作なので `CREDITS.md` には自作である旨を記す（ライセンス問題なし）
- 生成物はリポジトリにコミットする（パイプライン未実行の環境でも鳴るように）

「静かな土台＋演出で爆発」に合わせ、**通常操作の音は極めて控えめ、クリアだけ厚く**する。

## 9. マルチプレイ

### 9.1 制約から決まる方式

**Vercel では永続 WebSocket が使えない。** 外部サービスの追加は展示前のリスクが大きいので、
**1 秒ポーリング**で同期する。1 レース数分・同時 20 人程度なら負荷は誤差である。
Expo Go の制約にも触れない。

### 9.2 ルール

ホスト端末が部屋を作り、参加者は **QR かコード**で入る。全員が**同じ start / goal** を解く。
進行中は各参加者の「**今のランク**」だけが見える（打った語は見せない。真似で解かれると競技にならない）。
**最初にゴールへ到達した人が勝ち。**

### 9.3 データモデル

- `rooms` — `id` / `code` / `host_user_id` / `start` / `goal` / `status`(`waiting`|`playing`|`finished`) / 各種時刻
- `room_players` — `room_id` / `user_id` / `display_name` / `game_id` / `joined_at` / `finished_at` / `best_rank`

### 9.4 エンドポイント

| メソッド | パス | 用途 |
| --- | --- | --- |
| POST | `/api/rooms` | 部屋を作る（ホスト） |
| POST | `/api/rooms/:code/join` | 参加する |
| POST | `/api/rooms/:code/start` | 開始（ホストのみ） |
| GET | `/api/rooms/:code` | 状態の取得（**1 秒ポーリング先**） |

**レート制限**: 既存の `rateLimit` ミドルウェアは 1 秒ポーリングを弾く可能性がある。
**状態取得用に別枠の緩い制限**を設ける。ここを見落とすと展示中に部屋が固まる。

ゲーム本体は既存の `games` をそのまま使い、`room_id` で紐づける。
**ルール判定はサーバー**（既存の絶対制約）を維持し、順位はサーバーの `finished_at` で決める。

### 9.5 ブース動線

ホスト端末で部屋を作る → **コードと QR を大きく表示** → 来場者が参加 →
ホストが開始 → 全員の現在ランクが伸びていくのが見える → 最初のクリアで決着 → 結果一覧。

行列ができている状況で回せることが要件なので、**部屋の作り直しが 1 タップ**で済むようにする。

## 10. URL とロゴ

**URL**: 独自ドメインは両方とも生きている（`coto2ba-next.chotech.dev` / `coto2ba-next-api.chotech.dev` ともに 200）。
一方コード側は `constants.ts` が `*.vercel.app`、`landing/index.html` と `features/game/result.ts` が
`chotech.dev` と**食い違っている**。`packages/contracts/src/constants.ts` を正とし、
`app.json` の `extra.apiUrl` / `extra.landingUrl` を含めて全部揃える。
サーバー側の `BETTER_AUTH_URL` / `API_ORIGIN` / `LANDING_ORIGIN` の整合も確認する。

**ロゴ**: オリジナルのロゴ画像を使う（後日 "Next" 付きに差し替え予定）。
**アセットが未入手**なので、差し替え 1 手で済むようロゴ枠だけ先に用意する。

## 11. テスト方針

- **ルール層とヒントはユニットテスト**。特にヒントは §3.3 の改善率を数値で固定する
- **契約は契約テスト**。§3.1 の再発防止を含む
- **マルチプレイは統合テスト**。2 人が参加して先着が勝つこと、途中参加の扱い、ホスト以外が開始できないこと
- 既存の vitest 171 件と E2E スモークを**緑のまま維持**する
- UI は実機確認に依存するため、**Web プレビューで通ることを最低線**とする
