## [CONFIRMED] "Unicode's Normalization Stability Policy guarantees NFKC results never change for already-assigned characters, so the Python-15.0 vs Node-17.0 version gap can only diverge on codepoints assigned in U

**訂正後**: Substantially correct, with one range error and one caveat. Corrected: Unicode's Normalization Stability Policy (strong form, Unicode 4.1+) guarantees that a string containing only characters assigned in a given Unicode version, normalized per that version, normalizes identically under every later version — Decomposition_Mapping (canonical and compatibility) and Canonical_Combining_Class are immutable once assigned — so NFKC output for already-assigned characters is stable. The policy's own caveat is the flip side: strings containing code points unassigned in the older version may not be in normalized form under later versions. Therefore a Python-at-Unicode-15.0 (CPython 3.12) vs Node-at-Unicode-17.0 gap can diverge only on code points assigned in Unicode 15.1, 16.0 or 17.0 — not "16.0/17.0" only: Unicode 15.1 (Sept 2023) added 627 characters, 622 of them CJK Unified Ideographs Extension I (U+2EBF0–U+2EE5D). In practice those 15.1 additions are unified CJK ideographs with no compatibility decomposition and ccc=0, so NFKC output for them is identical either way; the error is in the stated range, not usually in observable behavior. Second refinement: divergence is *triggered* by a new code point but the differing output can include canonical reordering of adjacent already-assigned combining marks (the older build sees ccc=0 for the unknown character). Version mapping is exact: CPython 3.12 = UCD 15.0.0, 3.13 = UCD 15.1.0, 3.14 = UCD 16.0.0.

## [CONFIRMED] "React Native has no onCompositionStart/onCompositionEnd equivalent — the IME marked-text range is not exposed to JS. onChangeText fires for every composition update including unconverted かな, so '変換中'

**訂正後**: The technical substance is correct, but the citation is misattributed. Correct statement: React Native's TextInput exposes no composition events and no marked-text range to JS. The complete set of native TextInput events in RN core (ReactCommon/react/renderer/components/textinput/TextInputEventEmitter.h, main) is onFocus, onBlur, onChange, onContentSizeChange, onSelectionChange, onEndEditing, onSubmitEditing, onKeyPress, onScroll — there is no onCompositionStart/Update/End, and the event payload struct `Metrics` carries only { text, selectionRange, contentSize, contentOffset, contentInset, containerSize, eventCount, layoutMeasurement, zoomScale, responderIgnoreScroll, target }, i.e. no composing/marked range. On iOS, `markedTextRange` is read in RCTTextInputComponentView.mm only as an internal heuristic (to fall back to bare string comparison when deciding whether to reapply attributed text) and is never forwarded to JS. onChange/onChangeText is emitted from `-textInputDidChange`, which UIKit invokes while marked text is being edited, so unconverted かな reaches JS and "変換中" cannot be distinguished from committed text. Committing on onSubmitEditing/onEndEditing is a reasonable workaround, with caveats: on iOS onSubmitEditing is not called for some keyboardTypes (e.g. phone-pad) and multiline inputs do not fire it on Return, and onEndEditing also fires on blur — so both, plus an explicit confirm button, are usually needed.
