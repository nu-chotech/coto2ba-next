## 人間の判断が要るもの

### 1. NG 語リストが不十分（**展示前に必須**）
公開されている日本語の差別語リストは網羅的ではない。現在の `tools/pipeline/ng_words.txt` は:

- 手書き 125 語（差別・性的・暴力・薬物）
- MosasoM/inappropriate-words-ja (MIT): Sexual 281 語 + Offensive 49 語
- LDNOOBW ja (CC BY 4.0): 180 語

合計およそ 450 語で、**ほぼ性的表現に偏っている**。Offensive.txt は作者自身が「暫定版」と
書いている 49 行。暴力表現のカバーはほぼ無い。

**やること**: 展示前に人間が出力語彙とゴールプールを目視する。特に
`goal_pool.review_needed = true` の語。追記したら `pnpm pipeline:prune && pnpm pipeline:export`。

**影響**: 審査員・来場者の前に不適切な語が出る事故。

### 2. ゴール語の質は「人が選ぶ工程」なしには上がらない（要レビュー）
**品詞だけでは「政令」と「望遠鏡」を区別できない。** Wikipedia の頻度 500〜30,000 帯は
行政・法律・報道の語彙が厚く、機械的に選ぶとゴールが
「政令 / 官能 / 工法 / 目処 / 試料 / 市長選」になってしまう。

**やったこと**:
1. `vocab.is_concrete`（サ変可能・副詞可能・固有名詞・数詞・連用形名詞を除外）を追加
2. `tools/pipeline/goal_seeds.txt` に **人が選んだ 282 語**を置き、
   `04_goal_pool.py` がこれを先頭でボット検証し、`05_daily_schedule.py` が優先して消費する
3. 出力語彙に**漢字 1 文字を許可**（SPEC §4.2 は 2 文字以上だが、それだと SPEC 自身の
   例である「蚕」や 虹 / 鶴 / 亀 / 苔 / 琴 / 筆 が全部落ちる）

**やってほしいこと**: `goal_seeds.txt` に語を足す。展示で見せたい語を書けば、
次の `pnpm pipeline:goal-pool` でボット検証され、通ればデイリーに優先的に出る。
**展示日の goal は `daily_challenges` を直接編集して手で決めるのが正解。**

### 3. ゴールプールの easy が目標に届かない
ヒント追従ボットの実測で、候補の **91% が「ヒントに従っても 15 手で解けない」ため除外**され、
残った 9% のうち easy（bot_moves ≤ 4）は **0.5%** しか出ない。
SPEC §6.2 の「Easy 80」を満たすには 17,000 候補が必要だが、候補総数は 13,699。

**やったこと**:
1. **ボットの手数上限を 15 → 20（`MAX_MOVES` と同じ）にした。**
   プレイヤーは 20 手打てるのに 15 で切ると「実際には解ける語」を捨てていた。
   ratio も 3 段階 → 8 段階すべてを試すようにした
2. 難易度の区切りを 20 手基準に広げた: easy ≤5 / normal 6〜8 / hard 9〜17

**判断が要る点**: easy をもっと増やしたいなら、
(a) 難易度のしきい値を easy ≤ 5 に緩める、
(b) スタート語のランク帯 `START_RANK_RANGE` を [1000, 15000] に狭める（ゴールに近い所から始める）、
のどちらか。**(b) のほうがゲーム体験としては素直**（easy は「近くから始まる」であるべき）。

### 4. ゴール近傍の語を禁止したのは SPEC からの逸脱

通常のプレイには影響しないが、仕様と違うことは認識しておくこと。

## 推測で進めた箇所（理由付き）

### A. 出力語彙の「単一トークン」条件を緩めた
SPEC §4.2 は「MeCab で単一トークン」と書いているが、unidic-lite は
`潤滑油` → `潤滑` + `油(接尾辞)`、`銀河系` → `銀河` + `系`、`伝統芸能` → `伝統` + `芸能`
と分割する。単一トークン限定だと**ゲームに最も向いた名詞複合語が全滅する**
（SPEC 自身が「黄金の潤滑油」を表示名の例に挙げている）。

→ 「全トークンが 名詞/接頭辞/接尾辞 で、名詞を 1 つ以上含み、末尾が名詞か接尾辞-名詞的」
に緩めた。詳細は ARCHITECTURE.md §1。

### B. 出力語彙に freq_rank ≤ 180,000 の上限を追加
SPEC には無い条件。180,000 以降は `曽野木 / 羽ノ浦 / 優弥 / 紫山` のような
地名・人名の長い尾で、混合結果とヒントの質を落とす。
この上限で **99,805 語**になり、SPEC の「約10万語」という目標値に一致する。

### C. 認証を Bearer 運用にした（Cookie を使わない）
SPEC §7.4 は Better Auth の expo クライアント（SecureStore の cookie jar）を想定しているが、
調査で 5 系統の壊れ方の履歴が見つかり、失敗モードが常に「session が黙って null」だった。
また Expo Go のオリジン `exp://192.168.x.x:8081/--/` は DHCP 依存で安定しない。

→ **Better Auth はサーバー側でそのまま使い、クライアントは `set-auth-token` ヘッダで
受け取った Bearer トークンを expo-secure-store に自分で保存する。**
Cookie ヘッダが無いリクエストではオリジン検証がスキップされるので、
`exp://` の問題が構造的に発生しない。**本番で実証済み**（スモークテストに回帰テストあり）。

### D. `ratio` を丸めない
SPEC §5.3-2 は「ratio が 8 段階のいずれかであること。違えば 422」。
実装当初は `Math.round(v*10)/10` で丸めていたため 0.35 が 0.4 として通っていた。
**プレイヤーの意図を勝手に変えることになる**ので、厳密一致（浮動小数の誤差 1e-6 のみ許容）に修正。

### E. ランクは HNSW を使わず厳密全走査
pgvector の HNSW は近似なので、同じ盤面で rank が揺れる（実測: 厳密 9 に対し近似 7）。
**スコアが再現しないとランキングが壊れる**ので、最近傍探索だけ HNSW を使い、
ランクは 99,805 行のフルスキャンで数える。実測で十分速い。

### F. 表示名の NG チェックはしていない
`isAcceptableDisplayName` は長さと制御文字しか見ない。
語彙側で NG 語を除外済みなのと、ユーザーが手で入れた任意文字列を
形態素解析なしで判定するのは精度が出ないため。
**ブースモードでランキングに名前が載る**ので、気になるなら
サーバー側に部分一致の NG チェックを足すこと（`tools/pipeline/ng_words.txt` を
起動時に読んで Set にするだけで済む）。

### G. デプロイを Build Output API 直書きにした
SPEC §11.5 は `vercel build` → `vercel deploy --prebuilt` を想定しているが、
pnpm の `workspace:*` を npm が解釈できず **Vercel 側の install が必ず失敗する**。
tsup で全依存を 1 ファイル（2.9MB）に束ね、`.vercel/output` を自前で書き出して
install もビルドも不要にした。詳細は ARCHITECTURE.md §4。

### H. Vercel のリージョンを hnd1 ではなく sin1 にした
**Neon に東京リージョンは存在しない。** 一番近いのがシンガポール。
端末 → Vercel の 1 往復より、関数 → DB の往復のほうが回数が多い（1 手あたり数回）ので、
DB と関数を同居させるほうが速い。

## 解決済み

| 項目 | 結論 |
| --- | --- |
| Better Auth は Expo Go で動くか | **動く**。ただし Bearer 運用にすること（上記 C）。本番で実証済み |
| Expo Go に Skia / view-shot は入っているか | **両方入っている**（SDK 57）。一次ソースで確認済み |
| Neon の東京リージョン | **無い**。sin1（シンガポール）を使う |
| Postgres driver | `pg`（postgres-js は Neon の PgBouncer で named prepared statement が壊れる） |
| gensim は要るか | **要らない**。word2vec テキストの読み込みは numpy で 3 倍速い |
| 1 手の体感速度 | 本番実測 **456ms**。演出 600ms で覆えば体感は一定 |
