## 2026-09-19 ヒント候補プール（PR #5 / feat/hint-candidate-pool）

Issue #4 の提案どおり、**完成済みの 6 枠**ではなく**検証済み候補プール**を共有キャッシュに置くようにした。
`hint_candidate_cache`（migration 0008）に最大 16 件を持ち、ゲーム固有の除外は表示直前に効かせる。
これで同じ `(goal, current)` に別履歴で到達しても、先行ゲームの除外結果を引きずらない。

### レビューで見つけた劣化とその直し

PR の当初版は**ヒント上段の質を落としていた**。ベンチマーク（実語彙・決定論の 100 局面）で:

| | main | PR 当初 | 修正後 |
| --- | --- | --- | --- |
| 順位改善率 | 100% | 100% | 100% |
| クリア圏に着地 | **51** | **35** | **51** |
| 100 位以内に着地 | **99** | **85** | **99** |

原因は `vector.ts` の `hintCandidates`。`slice(0, HINT_VERIFY_LIMIT)` は **exclude を適用した後**に効くので、
`verifiedHintPool` が `exclude: []` を渡すと、`GOAL_NEIGHBOR_BAN` の 12 語が検証枠 16 の上位を占める
（あの語はコサインで最上位に並ぶ）。それを表示時に捨てるので、出せるのは弱い尾だけになっていた。

直しは `game.forbiddenInputs` をプール構築時に渡すこと。**これは `goal` だけの関数**
（`goalNeighborhood(goal, GOAL_NEIGHBOR_BAN)`）なので、共有キャッシュの前提は壊れない。
Issue #4 も「保存前に除外してよいもの」に「goal 由来の禁止語」を挙げていた。

**この劣化は CI では捕まらない。** 閾値が characterization の幅（`MIN_WITHIN_100_SHARE = 0.8`、
`CLEAR_SHARE_RANGE = [0.2, 0.9]`）なので 85/35 でも通るし、そもそも**ベンチマークは DB が要るので CI では skip される**。
ヒントの計算を触ったら、ローカル DB でベンチマークを回して上の表と突き合わせること。

### 残り

- キャッシュ版は `HINT_CACHE_VERSION`（contracts に集約、現在 3）。候補の作り方を変えたら上げる
- 救済経路（通常候補が全滅したとき）が持つのは **1 件**。プール化の利点がここだけ効かない
- 強度別表示（弱・中・強から各 2 件）は未実装。Issue #4 に残している

## 2026-09-18 の改修（feat/exhibition-ux）

実機を触ったオーナーのフィードバックを起点に、8 本の計画を並列で実行した。
すべてレビューを通してからマージしている（レビューの記録は `.superpowers/sdd/exhibition-ux/`）。

### ゲーム内容

- **ヒントを外挿ベースに作り直した。** 従来は `0.8×現在 + 0.2×ゴール` の近傍（内挿）を返しており、
  混ぜても結果がほとんど動かなかった。1 手は `blend(current, 1-r, input, r)` なので、
  ゴールに着地させる入力語は外挿 `(v_goal − (1−r)·v_current) / r` の方向にある。
  **改善率 44/100 → 100/100、rank 改善幅の中央値 −1061（悪化）→ +14562。**
- **ランキングを「ヒント数 → 手数 → クリア時刻」に変更。** ヒントが強くなりすぎたため、
  ヒントの使用をランキングで課金する形にした（ノーヒント 15 手がヒント 1 回 3 手より上）。
- **ヒント候補の表示順を決定的にシャッフル。** 1 位が常に勝ち確定の手になるのを避ける。
  完全錬成 37/100 → 4/100。
- **自己ベストを (ヒント数, 手数) の辞書順に。** ヒント 1 回で「1 手」が永久に残り
  更新不能になっていた。

### 見た目と操作

- **絵文字を全廃し SF Symbols に**（シェアテキストの `⬜🟩🟦🟨` は意図的に残す）
- **Liquid Glass を主要な操作面に統一**（`GlassButton`）
- **ライト/ダーク両対応。** 図鑑だけは宇宙なのでライトでも暗いまま（意図的な例外）
- **余白とタイポグラフィを Apple のメトリクスに**（Large Title 34 / 本文 17 / 最小タップ 44pt）
- **ロゴを入れ、スプラッシュ・アプリアイコン・OG 画像をロゴから自動生成**
  （`icon.png` 799KB → 35KB、splash が 228×213 の空白からロゴのマークに）
- **比率の指定を iPod 風の回転ホイールに戻した。** 円周 154.3° でちょうど 4 段、270° で端から端
- **ギブアップを見つけやすい場所に**（旧実装は Alert の 2 段重ね）

### 図鑑

- **主役を点群から「自分の軌跡」に。** `start → 各手 → goal` を光らせ、点群は背景に降格
- 開いた瞬間に経路が画面に収まるようカメラを自動フレーミング
- 上部を検索ではなく経路の切り替えに
- 結果画面から「この軌跡を見る」で該当経路にフォーカスして開く
- **本番 DB に pos3 を投入済み**（102,520 語）。これまで全語 NULL で図鑑にデータが出なかった
- **ライトモードで読めなかったのを直した。** 地はダーク固定なのに `GlassCard` が端末の
  スキームを読み、暗い宇宙の上に紙色の面が出て補助文字が **2.52:1**（実測）まで落ちていた。
  `ThemeProvider` にサブツリーの scheme 上書きを足し、**境界は `(tabs)/space/_layout.tsx` の
  1 箇所**に。図鑑の中の部品は `useTheme()` を素直に呼べばダークのパレットを受け取る

### マルチプレイ（対戦ルーム）
- `POST /api/rooms` / `POST /api/rooms/:code/join` / `POST /api/rooms/:code/start` /
  `GET /api/rooms/:code`（**ポーリング専用のレート制限バケツ**）
- お題は部屋で 1 度だけ抽選して全員に配る。**進行中に他人が打った語は返さない**
- 勝敗は `games.cleared_at`（サーバーの時刻）。全員終了か最初のクリアから
  `ROOM_FINISH_GRACE_SECONDS` で部屋を畳む。放置された部屋は `ROOM_TTL_MINUTES` で掃除
- 端末側は `/play/room`（入口）→ `/play/room/[code]`（待機・結果）→
  **既存のゲーム画面に順位のオーバーレイを重ねる**（画面を複製していない）
- **落とせる**: `app.ts` の `app.route('/api', roomsRoutes)`、ロビーの「みんなで対戦」、
  ルートの `RoomDeepLinkGate`、`playMove` の `roomStandingsForGame` の 4 か所で切り離せる

### 効果音

- 10 種を Python で合成して同梱（`pnpm pipeline:sounds`）。ライセンス問題ゼロ、音色を統一
- 全音のエッジが厳密に 0（クリックノイズなし）、3〜5kHz のエネルギー 0%、クリッピングなし

### 直したバグ

- **設定画面が「サーバーの応答を解釈できません」を出す**
  （Zod 4 の `z.record(enum, …)` は列挙キーの網羅を要求する。`best_free_moves` が `{}` だと必ず落ちる）
- **`pnpm lint` がずっと失敗していた**（`apps/api/src/db/client.ts:34`、最初のコミットから存在）
- **`/api/me` が 1 リクエストでレート制限のトークンを 2 つ食っていた**
  （Hono の `use('/x/*')` は `/x` にも一致する）
- **アプリ起動時に自分自身のレート制限で 429 が出ていた**
  （トークンバケットの容量と補充レートに同じ定数を使っていた）
- **Web で認証できず一度も遊べなかった**（`expo-secure-store` の Web 実装は空スタブ）
- 公開 URL が `*.vercel.app` と `chotech.dev` で食い違っていた

## 注意していること

### ⚠️ 対戦ルームのポーリングと Hobby の invocations 枠

対戦ルーム（設計 §9）は WebSocket を使わず 1 秒ポーリングで同期する
（採用しない理由は `docs/QUESTIONS.md` §8）。**Hobby は枠を超えると
従量課金ではなく API 全体が 30 日停止する**ので、消費を見ておくこと。

**ローカルの実測**（`python3 apps/api/tests/load.py --scenario room --seconds 60 --users 8`）:

| 項目 | 実測 |
| --- | --- |
| ポーリング（GET /api/rooms/:code） | 8 人 60 秒で 459 件（= 1 人 0.96 req/s） |
| 手（POST /moves） | 112 件 |
| 429 | **0 件**（ポーリングは専用バケツ 4 req/s、手は汎用 5 req/s） |
| p95 | ポーリング 30ms / 手 96ms |

**1 レースあたりの見積もり**（8 人・ロビー 60 秒 + レース 180 秒）:

| 内訳 | 計算 | 回数 |
| --- | --- | --- |
| ロビーのポーリング（2.5 秒間隔） | 8 × 60 / 2.5 | 192 |
| レースのポーリング（1 秒間隔） | 8 × 180 / 1 | 1,440 |
| 手とその後の再取得（1 手につき最大 4 本） | 8 × 10 × 4 | 320 |
| 部屋の作成・参加・開始 | — | 約 10 |
| **合計** | | **約 2,000** |

**8 時間の展示に掛けると**: 1 レース + 入れ替えで約 5 分 → 12 レース/時 →
8 時間で約 96 レース → **1 日あたり約 19 万回**。3 日なら **約 58 万回**で、
Hobby の月 100 万回に対して**残りは約 4 割**（ここに 1 人用プレイぶんが乗る）。

**余裕が無いときのつまみ**: `ROOM_POLL_INTERVAL_RACE_MS` を 1,000 → 1,500 にすると
いちばん大きい項（1,440）が 960 に減り、1 レースが約 1,500 回になる。
体験への影響は「順位バーの追従が 0.5 秒遅くなる」だけ。

**展示前日にやること**: Vercel の Usage で invocations と Active CPU を見て、
上の見積もりと突き合わせる。**この確認はまだ行っていない**（機能が未デプロイのため）。
